01 / THE APPLIANCE

CodeQL General Appliance — CGA

CGA is a collection of shell utilities for using CodeQL across collections of projects: prepare databases and queries, apply queries through multi-repo variant analysis (MRVA), and examine the results without losing their origin.

The shell is the interface. A person or an agent can use the same commands, inspect the same recorded state, and follow a finding back to the query, database build, submission, and ingestion that produced it. Browser views provide another way into that evidence, not a separate workflow.

FOLLOW THE EXAMPLE

Five milestones. One shell.

Open each milestone in order. Run one command line at a time in your terminal. The numbered recipes supply the exact Bash commands; there are no inputs to choose on this page.

Before starting: use Linux with cga on PATH, CodeQL with C++ libraries, and DuckDB. See the installation steps below if needed. Downloads need network access and disk space.

Use a fresh sample workspace. Setup reclaims shared MRVA ports and resets its PostgreSQL state: do not run it alongside Bench or another MRVA scenario.

01 Start the workbench Sample steps 00–04 · supporting setup

Create the sample directory and recorded workflow, then prepare and start MRVA. The build here is for the MRVA server and agent, not for CodeQL databases.

cga h s 05 00 rCreate workspace
cga h s 05 01 rPreflight
cga h s 05 02 rReset MRVA
cga h s 05 03 rBuild MRVA
cga h s 05 04 rStart MRVA

You now have: a workflow under cga/cga-tmp/help-sample-05/ in this checkout, and running MRVA services. Step 00 refuses an existing sample directory.

02 Bring the inputs together Sample steps 05–11 · the Inputs lane

Index the existing catalogue and query library. Inspect them, apply the fixed selections, download the five prepared database archives, and pack Fprintf.ql.

cga h s 05 05 rIndex libraries
cga h s 05 06 rLook at queries
cga h s 05 07 rLook at databases
cga h s 05 08 rSelect five databases
cga h s 05 09 rSelect Fprintf.ql
cga h s 05 10 rDownload databases
cga h s 05 11 rPack the query

You now have: five selected databases and one executable query pack, recorded for user bob.

03 Run the analysis Sample steps 12–15 · the Workflow lane

Submit once. Observe the submission until it succeeds, then download and verify its result archives.

cga h s 05 12 rSubmit once
cga h s 05 13 rObserve status; repeat until succeeded

Continue only when status is succeeded. If it fails, investigate. If interrupted or unsure whether submission completed, inspect status instead of repeating step 12.

cga h s 05 14 rDownload results
cga h s 05 15 rVerify archives

You now have: five verified result archives for submission sample-05, each containing a SARIF file.

04 Collect and read the results Sample steps 16–18 · the Outputs lane

Ingest each SARIF into SQLite and combine the five into DuckDB. Verify the store, then run the supplied SQL to see up to four findings per database.

cga h s 05 16 rIngest and combine
cga h s 05 17 rVerify ingestion
cga h s 05 18 rRead findings by database

You now have: findings/all.duckdb in the sample workspace, and a per-database preview with total counts. A successful job with no findings gets an explicit zero-findings row; it does not disappear.

Fprintf.ql demonstrates the pipeline. Its findings are not proof of vulnerability detection.

05 Stop, without losing the work Sample steps 19–20 · retain the evidence

Check the MRVA server log, then stop its services. The workflow history, downloaded results, SQLite databases, and DuckDB remain.

cga h s 05 19 rCheck server log
cga h s 05 20 rStop services

You retain: the inputs, the recorded execution, and the results. Stopping is not cleanup or deletion.

FOLLOW THE EVIDENCE

Look inside.

These are the diagram’s doorways, also available as ordinary expandable sections. They explain the fixed example, not a live run.

Inputs / five prepared databases

INPUTS / DATABASES

Already built. Selected, then downloaded.

The fixed SQL selects one C++ database archive for each repository:

  • dsvpn/dsvpn
  • file/file
  • flex/flex
  • inotify-tools/inotify-tools
  • nnn/nnn

Selection uses the existing catalogue. Step 10 downloads the chosen archives; this example does not build CodeQL databases.

Read the selection SQL or follow sample steps 05–11.

Inputs / Fprintf.ql

INPUTS / QUERY

One supplied query. No authoring detour.

Step 09 selects Fprintf.ql from the indexed query library for user bob. Step 11 builds its executable query pack.

The same pack is applied to all five databases. This is a pipeline demonstration, not a claim that the query detects a particular vulnerability.

Follow sample steps 05–11.

Workflow / one submission, five jobs

WORKFLOW / MRVA

One request, applied five times.

Submission sample-05 runs as user bob. It pairs the query pack with each selected database, producing five database jobs.

Submit once, observe status until succeeded, download the result archives, then verify them. Human and agent use the same shell commands and recorded workflow.

5 databases × 1 query pack = 5 jobs

Follow sample steps 12–15.

Outputs / raw SARIF

OUTPUTS / RAW RESULTS

The original result for each job.

Each downloaded result archive contains results.sarif. Ingestion extracts and retains the SARIF with its job provenance. Five successful database jobs provide five SARIF inputs.

Si,j = SARIF(databasei, query packj)

Here there is one query pack, so j = 1. A pack can contain several queries; SARIF is per job, not necessarily per individual query.

An empty findings list can be a valid successful result. It is different from a missing result or a failed job.

Download and verify in steps 14–15.

Outputs / individual SQLite databases

OUTPUTS / INDIVIDUAL RESULTS

One SARIF becomes one SQLite database.

Step 16 converts each SARIF independently. This preserves the boundary between the five database jobs while making their results queryable.

Si,1 → SQLitei,1

The recorded ingestion keeps each job’s repository, status, finding count, and archive, SARIF, and SQLite paths. These records connect combined findings back to their origin.

Ingest and verify in steps 16–17.

Outputs / cumulative DuckDB

OUTPUTS / COMBINED RESULTS

One place to query all five jobs.

The same ingestion step combines the recorded SQLite inputs into findings/all.duckdb. For this fresh, single-run example, that means the five jobs from sample-05.

In general, the store is cumulative across all recorded ingestions, not every SQLite file found on disk.

Step 18 uses the supplied results SQL to show total counts and up to four findings per database in stable source-location order, including explicit zero-findings rows.

Read the results in steps 16–18.

The shell is the escape hatch.

This page deliberately has no configuration. To see the exact Bash for any step before running it, omit the final r:

cga h s 05 08Display the database-selection recipe

Displaying a recipe changes nothing. Adding r runs exactly its displayed Bash. Once you understand the example, use the underlying commands in your own shell workflow; customization belongs there.

Host installation commands

GETTING STARTED / HOST

Prepare the tools in a Linux VM.

Use a dedicated VM for experiments. The commands below install software and enable PostgreSQL only when you run them in your terminal; the browser just displays them.

Get the repository

In the VM, install Git if needed and clone the checkout:

sudo apt-get update
sudo apt-get install -y --no-install-recommends git ca-certificates
git clone https://github.com/hohn/codeql-general-appliance.git
cd codeql-general-appliance

Already have a checkout? Use it instead. Run only the installer matching the VM’s distribution.

Ubuntu 24.04 Noble

From the checkout, inspect the required packages and cached tools, then install them: 

./vm-setup/ubuntu-noble/install-dependencies.sh --list
./vm-setup/ubuntu-noble/install-dependencies.sh

Debian sid

./vm-setup/debian-sid/install-dependencies.sh --list
./vm-setup/debian-sid/install-dependencies.sh

Both installers use sudo as needed and install the required environment, including the CodeQL bundle. Sample 05 uses filesystem storage; optional MinIO is not needed for this example.

Start a new login shell after installation, or load the installed CodeQL profile into the current shell: 

. /etc/profile.d/mrva-codeql.sh

Details: Ubuntu installer, Debian installer, or the manual dependency guide for other supported Debian/Ubuntu setups.

Next: install the CGA command.

CGA command installation

GETTING STARTED / CGA

One dispatcher, linked to the checkout.

From anywhere inside the repository checkout, install the user-level command and Bash completion: 

repo_root=$(git rev-parse --show-toplevel)
install -d "$HOME/.local/bin"
ln -sfn "$repo_root/cga/cga" "$HOME/.local/bin/cga"
install -d "$HOME/.local/share/bash-completion/completions"
ln -sfn "$repo_root/cga/completions/cga.bash" \
  "$HOME/.local/share/bash-completion/completions/cga"
export PATH="$HOME/.local/bin:$PATH"
cga --help

If $HOME/.local/bin is not already on your login PATH, keep that export in your shell profile too. The symlinks point into this checkout, so moving or deleting it requires recreating them.

Enable completion in the current Bash shell:

source "$(git rev-parse --show-toplevel)/cga/completions/cga.bash"
