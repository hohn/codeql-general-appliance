Advanced reading guide

This guide assumes practical CodeQL experience: databases, query packs, SARIF, and reading shell workflows. It is intended for experienced humans and LLMs, not as an introduction to CodeQL or CGA. Audience markers below do not imply beginner accessibility.

For a first look and a fixed worked example, start with the CGA overview, then use CGA help for tasks and commands. The introductory guide offers additional usage outlines; the reference manual collects detailed material.

This repository is a science experiment and an evolving prototype, not a finished software product. Its purpose is to handle CodeQL databases and queries, apply queries to databases, and help humans and LLMs investigate the results. The code makes those activities possible; usage, examples, and their explanations are equally important. Code and examples evolve together.

Use this guide to choose a small reading path, not to read the repository cover to cover. The paths point into existing documentation; they are not additional tutorials or instructions to launch services.

How to read

[Both] is useful to humans and LLMs, [Human] emphasizes explanation and interactive exploration, and [LLM] emphasizes bounded discovery and implementation constraints. These are reading hints, not access restrictions.

Start means the initial reading for that question. Reference means follow the link only when the question needs that detail. Stop identifies what you should understand before returning to your experiment or task.

[LLM] This is the broader project map, not mandatory onboarding. Read the short agent core once, then use the CGA LLM entry guide for CGA work or the core’s matching topic for other tasks. Return here only if that focused route and component-local investigation cannot establish ownership.

When that fallback is needed, choose one question below. Read named sections, not entire documents or the example catalogue. Follow other component links only when evidence crosses their boundary. For an existing experiment, inspect its bounded state projection before reading implementation code or raw artifacts.

Orientation [Both]

The main activities are:

Activity What it contributes Starting document
Prepare inputs Acquire sources, build and validate CodeQL databases, materialize queries, publish catalogues Preparation
Apply queries Select databases and query packs, submit MRVA jobs, download results CGA
Investigate and compare Work with accepted inputs, frozen results, and explicit experiment comparisons Bench
Retain and explain evidence Record workflow steps, provenance, SARIF ingestion, and human/LLM exports CGA workflows

CGA is the command interface joining these activities. MRVA is the execution system: a server schedules query evaluations across databases and workers return SARIF. Bench provides an experiment/session interface. Preparation and analysis exchange artifacts explicitly; they do not share one mutable session.

Reading paths

Understand an end-to-end analysis [Both]

Question: How do selected databases and a query become inspectable results?

Start: Read the introduction and Flow in the single-user MRVA example, then read its driver alongside that sequence.

Reference: CGA State explains the state passed between operations. Follow only the component README for the step you are exploring. Read the example’s Run it section before actually running it: it manages shared infrastructure and leaves services available for inspection.

Stop: You can identify database selection, query packing, execution, ingestion, and export, and distinguish setup/teardown from the analysis.

Explore query or database changes [Both]

Question: What changes between sessions, and what makes a comparison valid?

Start: Read Experiment purpose and contract (humans and LLMs) and Session actions in the Bench guide.

Reference: Continue to that guide’s commands and human/LLM interfaces for your chosen interaction. Read Bench operational notes only for implementation changes, recovery, or viewer lifecycle questions.

Stop: You can explain the fixed versus changing input, S1 as the reference, the D/Q/J/R cells, and why running a session and comparing results are different operations.

Prepare databases and queries [Both]

Question: Where do analysis inputs come from, and how are they handed over?

Start: Read the preparation introduction and its explicit handoff. For a concrete worked sequence, read Componentized preparation in the query-030 example.

Reference: Use the CVE catalogue to choose another case. Read only the relevant preparation command’s README when changing source acquisition, database construction, validation, or indexing. Preparation notes cover campaign and storage constraints.

Stop: You can locate source/database/query provenance and explain which artifacts are explicitly imported into a separate analysis workflow.

Investigate findings and supporting evidence [Both]

Question: What does this result establish, and where is its evidence?

Start: Read named ingestion and the export contract. For an actual investigation, read the zlib study and choose one query checkpoint rather than reading all of them.

Reference: The analysis evidence index points to preserved collection runs; their query-effectiveness reports distinguish candidate findings from demonstrated CVE detections. Large evidence trees live outside Git; follow their manifests, not a recursive artifact dump.

Stop: You can trace a finding to its query, database, submission, and ingestion, and distinguish successful execution, zero findings, and detector effectiveness.

Inspect an existing experiment or workflow [LLM]

Question: What is already selected or completed, without re-reading or rerunning everything?

Start: Read Assistant context. Use cga llm context bench for experiment/session state or cga llm context unified for the workflow outline, in the relevant workspace. These are read-only and do not need a running web server.

Reference: Follow the returned documentation or resource references. Visual element identifiers explain shared addresses for CLI and UI facts. Unified outline and search provides more targeted discovery.

Stop: You know the current inputs, completed work, and unresolved step. Open full source, state, or result artifacts only to answer a specific remaining question.

Evolve a usage example [Both]

Question: How should a new or changed experiment express its operations?

Start: Read the flow script guide, then choose the closest example below.

Reference: Read CGA Workflows and State when changing recording or composition. CGA notes describe non-obvious integration constraints.

Stop: Each meaningful operation and experimental choice is visible, with explicit inputs, outputs, lifecycle, and provenance. Change supporting code and usage documentation together when the example needs new behavior.

Change or debug the supporting code [Both]

Question: Which implementation owns the behavior observed in the example?

Start: Locate the example’s failing or changing operation first. Use CGA Layout for command ownership or the root README’s MRVA component map for server, worker, scheduling, and storage behavior.

Reference: Read only the matching agent topic: runtime, CGA, Bench, preparation, or views. Read system-test notes before using an e2e driver, and environment notes before host setup.

Stop: You have identified the owning operation, state contract, and smallest relevant check. Read another subsystem only if the evidence crosses that boundary; retain a usable example alongside implementation changes.

Structural conventions [Both]

Convention Where to learn the details
Use the top-level cga dispatcher for recorded workflows; direct component binaries remain JSON-in/JSON-out filters Commands and state
.cga/ holds workflow metadata/history and local runtime/scratch; the configured content-addressed store holds objects Workflows
Many Python components use bin/, a same-name package, and tests/; some preparation services use bin/lib/doc/share instead CGA layout, controller
Server and worker are separate Go modules using the sibling mrvacommander shared module; other utilities may have their own modules MRVA component map
PostgreSQL holds operational state and references, not large database/source/result blobs Runtime storage notes
Operator overrides survive defaults; lifecycle ownership and setup/analysis boundaries stay explicit Agent core
Usage documentation stays near examples/components; the book links canonical Markdown through symlinks Documentation notes

Examples and fixed checks [Both]

Everything here is prototype material. “Starting example” means a useful entry point today, not production readiness. Keep earlier examples when they offer a different experimental shape or could be expanded.

Examples leave room for experimentation. E2e tests are a special case of examples with fixed inputs and assertions that test the code. Passing a fixed check does not by itself demonstrate that a scientific detector is effective.

Further reading and maintenance

[Human] The project book assembles component and usage documentation for browsing. Conceptual notes form a separate book; consult them for a specific idea rather than as required onboarding. Installation and remote access are references for running experiments, not prerequisites for understanding them.

[Both] Keep this guide a routing layer. Put detailed usage beside the example, implementation contracts beside the component, and non-obvious operational constraints in the relevant agent topic. Update these links when an example or command changes. Remove out-of-date documentation rather than creating a documentation archive; Git retains earlier versions. Preserve the examples themselves for further experimentation.
