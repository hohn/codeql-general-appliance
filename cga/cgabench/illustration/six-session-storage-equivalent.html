Six-session storage equivalent

This is a hand-kept experiment notebook for the same six-session query-study illustrated by the linear shell sequence. It collects the data and connections a person would need to retain, not every CGAST checkpoint, command response, editor setting, or intermediate draft. The records below describe the actual accepted artifacts in my-bench, active chain cga_1; the shell illustration’s friendlier filenames are not their on-disk names.

The sections are nodes in the storage graph. A session connects an accepted database and query to a submission; that submission connects to results; the comparison connects selected result snapshots back to their inputs. A filename or a finding count alone is not enough to recover those connections.

Path convention: W means cga/cgabench/my-bench, relative to the repository root. T means W/.cga/tmp. File links are relative to this document and point to existing local artifacts, many of which are not committed to Git. This is an index, not a portable archive: it does not copy or relocate those files.

What each result representation preserves

The edges within every R section have different meanings:

submission + repository
    -> downloaded result ZIP
        -> results.sarif
            -> per-job SQLite -> session all.duckdb
            -> frozen findings/provenance JSON -> comparison C

The result ZIP contains results.sarif; the separately retained .sarif file is its extracted copy. SQLite and DuckDB expose the ingested findings for SQL. The frozen JSON preserves each finding’s identity, SARIF result, and provenance, plus ingestion information.

That provenance connects a finding to its Bench session/name, user, submission, MRVA session, repository, SARIF path, and zero-based run and result indices within that SARIF. The session record connects it further back to D and Q. The frozen result document is not a complete substitute for that input index.

Identical basenames recur throughout the study. Each result ZIP is named AFLplusplus-AFLplusplus.zip; each job has the same SARIF/SQLite basename; every session SQL store is named all.duckdb. The enclosing session/job directory is part of the identity. Putting them in one folder without renaming or keeping these connections would lose which run they came from.

SQL stores and their scope

Each linked SQLite and DuckDB has a sarif_results table with columns:

user, file_name, kind, rule_id, rule_name, uri,
start_line, start_column, result_json

result_json retains the SARIF result object. The SQL database is therefore more than a count or a summary table. The Findings popup uses the selected session’s DuckDB; its separate result-summary tab shows counts derived from the ingestion records.

Although the filename is all.duckdb, each of these six stores contains only its own session’s ingestion. There is no study-wide combined SQL store here. Each session has one repository/job, hence one per-job SQLite input.

For example, from the repository’s cga/ directory, this reads S6 without changing it:

duckdb -readonly -safe -no-init -bail \
  cgabench/my-bench/.cga/tmp/cgasi-y2voc79o/all.duckdb \
  -c 'SELECT rule_id, count(*) AS findings FROM sarif_results GROUP BY rule_id;'

It reports cpp-fprintf-call with a count of 116. If combining stores by hand, attach an explicit session label before unioning records: user, file_name, and rule_id repeat across sessions and cannot identify a trial.

The Databases, Queries, and Result summary SQL popups are different again: they materialize temporary DuckDB tables named databases, queries, and result_summaries from accepted evidence. Those databases are discarded after the request; they are not additional retained experiment/comparison stores.

Comparison C

Important distinction: the current Bench does not create a separate comparison SQL database. It reads the frozen findings JSON snapshots and writes a comparison JSON document. The six DuckDBs above are retained SQL findings stores, not six materialized comparison databases.

For a hand-built SQL comparison, the user would additionally retain the session-to-database mapping, baseline/input list, SQL or view definitions, identity/multiplicity policy, and saved output. Merely keeping all.duckdb or subtracting counts would not preserve this comparison.

What a person would keep, rather than all CGAST state

Keep by hand Why
This experiment/session index and D/Q/J/R/C links Preserve the graph: what ran against what, and which results were compared
The accepted D selection, archive identity/hash, and archive or a verified way to retrieve it Identify the actual analyzed code/database, not today’s catalogue entry
Each accepted query selection and pack, with hashes Preserve the selected query and executable inputs, including dependencies, independently of drafts
Actual findings: the SQL stores and frozen result snapshots Retain inspectable results and the comparison-ready identities/provenance
A raw SARIF form, preferably ZIP or extracted SARIF Recommended for full-report inspection, independent re-ingestion, and following original-report provenance
Comparison document(s), input list, baseline, and comparison policy Preserve the conclusions and their derivation, not just displayed totals

Raw SARIF is not required merely to query an existing SQL store or compare already-frozen R snapshots. Keeping it is nevertheless useful: result_json and frozen finding objects do not preserve the entire SARIF report’s tool/rule/run metadata. ZIP and extracted SARIF duplicate the report; a manual archive could keep one raw form and document how to recover the other.

SQLite and DuckDB also overlap: DuckDB is rebuilt from the ingested per-job SQLite files. A manually curated archive could choose a canonical retained representation plus a regeneration recipe instead of keeping every derivative. This notebook lists what is actually retained, not a deletion plan for the running Bench.

There is no need in such a notebook to preserve every unsuccessful draft, editor port, disclosure state, service-check response, polling response, or whole-CGAST revision just to understand the completed study. Recovery while a job is in flight is a separate concern; this index does not replace execution checkpoints.

The awkward part is not storing six reports. It is preserving every edge: which database bytes, which accepted query bytes, which remote job, which report, which SQL projection, and which comparison inputs. Paths under .cga/tmp here are live retained evidence, despite the name. Removing them or copying only the state JSON would leave missing targets. Moving the experiment by hand requires copying the chosen artifacts and updating all these links and provenance paths; this document does not perform that migration.
