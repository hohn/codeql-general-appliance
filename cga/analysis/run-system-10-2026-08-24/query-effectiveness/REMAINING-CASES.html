Query effectiveness: remaining 16 CVEs

Conclusion

All 16 remaining cases fail as CVE detectors. Eleven produce no findings in any source variant or database mode. The other five produce 649 findings, but no vulnerable or patched result location or path step enters the known fault file. None qualifies even as the file-level “almost found” seen in the zlib positive-control query.

Together with the initial three-case review, the collection result is:

Assessment CVEs Meaning
Directly found 0 No result identifies a known vulnerable operation.
Almost found 1 The zlib query selects the right file only; it cannot distinguish variants.
Not found 18 No result reaches the known fault, or the query emits no result.

This supports calling the existing query set a failure for CVE detection. It does not mean every reported generic issue is false, or that CodeQL cannot express suitable queries. It means these query definitions and CVE mappings do not validate the known vulnerabilities in this corpus.

Query-level diagnosis

cpp/overrun-write

This query is assigned to nine CVEs including libarchive. Across 54 successful analyses it emits zero results. Its implementation is substantially narrower than its CVE assignments: it requires product flow between a heuristic allocation’s simple size expression and a modeled array-function write whose size exceeds the allocation by a computed constant delta. Several assigned CVEs are reads or invalid dereferences, and even the true write-overflow cases do not necessarily have this allocation/write shape.

cpp/tainted-format-string

Across fmtlib, jhead, and Irssi, only jhead emits results—seven paths to an unrelated command-line-controlled sprintf() format argument. The query is specifically taint flow from a recognized external source to a printf-family format argument. It cannot detect a literal but invalid format specifier, an undersized formatted-output destination, or an escape-parser out-of-bounds read merely because those faults were labeled CWE-134.

cpp/tainted-arithmetic

This query emits all 649 generic findings in the remaining set, spread across five CVEs; SDL_image emits none. Result volume does not correlate with the known faults. Vulnerable and patched counts are identical for memcached, libgit2, libpng, and lighttpd. Libssh2 has a vulnerable-only count increase in none mode, but every result is in misc.c, while the repair is in kex.c. The query’s low-precision, broad taint-to-arithmetic model creates many review leads without providing CVE identity or variant discrimination.

CVE-specific zlib location query

The custom query is a useful analysis-pipeline positive control, but its only predicate is the filename crc32.c. It accounts for the collection’s sole “almost found” classification and should not be included in a detector success rate.

Implications for the test design

The six-database matrix and preserved SARIF are useful; they exposed the failure clearly. The weak point is treating a broad CWE query as a CVE query. Future acceptance should require, for each CVE:

  1. a source-level oracle naming the vulnerable operation and repair;
  2. a query result whose primary location or path reaches that operation;
  3. vulnerable-to-patched discrimination within at least one build mode; and
  4. an explicit explanation when current-source results represent a different issue rather than persistence of the CVE.

Until a query passes those checks, its output should be labeled a generic candidate search, not a CVE detection result.
