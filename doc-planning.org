* Turn 1: User

we now have extensive docs (good) but with one major problem (for humans): no clear reading order. One choice that comes to mind: group the 'cga' commands into |database creation| database application |query writing| result review |, then align the book/ content to that. Thoughts?

* Turn 2: Assistant

*Yes—organize around what the reader wants to accomplish, not which component implements it.* The current book starts with guides, then switches to a component inventory; readers must reconstruct the workflow themselves.

Your four groups make sense. I would change “database application” to *“Apply queries”*: databases are inputs, while running queries is the activity.

| Book part                 | Reader's goal                                                    | Main CGA commands                                        |
|---------------------------+------------------------------------------------------------------+----------------------------------------------------------|
| *Create databases*        | Turn source into validated databases and a catalogue             | =src-prep=, =database=, =catalog=                         |
| *Write and prepare queries* | Develop queries and package selected inputs                    | =coder=, =query-gen=, =query-lib=                         |
| *Apply queries*           | Select databases and queries, submit analyses, retrieve results   | =db-lib=, =query-lib=, =mrva-request=                     |
| *Review results*          | Inspect findings, trace evidence, compare experiments, export     | =sarif-ingest=, =export=, =unified-view=, =bench=          |

These are *task groups, not exclusive command categories*. =query-lib= bridges preparation and execution; Bench spans query iteration, execution, and comparison. Cross-link those rather than forcing each into exactly one box.

For a clear reading order, I suggest:

1. *Start here:* a short system picture and one complete example using existing databases and a supplied query. Reach an inspectable result without first learning database construction.
2. *The four task parts above:* each starts with prerequisites, a core command sequence, expected outputs, and where to go next. Database creation and query writing are independent inputs to query application—not mandatory consecutive lessons.
3. *Reference:* complete command help, workflow/history concepts, installation, service operation, architecture, and contributor material.

The distinction is important: *the first reading path should be short; the book should still cover the whole lifecycle.*

We already have useful foundations in =guides/introductory/cli-workflow.md= and the worked examples. I would reorganize the book's =SUMMARY.md= around these tasks, adding only short connective chapters where needed and retaining canonical component documentation through the existing symlinks. The advanced reading guide would remain a task index, not another competing tutorial.

For the HTML help browser, the same groups could organize the left tree, with an additional *Workflow and operations* group for commands such as =init=, =chain=, =store=, and service management. That aligns navigation without renaming commands or changing their behavior.

as an aside, how do we structure LLM docs?

* Turn 4: Assistant

*Share the factual documentation; give LLMs a different entry path.* Humans need a learning sequence; LLMs need to locate the relevant contracts and evidence with minimal reading.

The existing structure is a good foundation:

| Layer                | Purpose                                                                         | Current location                                 |
|----------------------+---------------------------------------------------------------------------------+--------------------------------------------------|
| *Core*               | Mandatory invariants, essential prohibitions, routing instructions; kept short   | =.agent-notes/README.md=                          |
| *Task routing*       | Where to start, what to consult, when to stop reading                            | =READING-GUIDE.md=                               |
| *Topic contracts*    | Non-obvious constraints, ownership boundaries, failure modes, relevant checks     | =.agent-notes/*.md=                               |
| *Shared reference*   | Command behavior, examples, architecture; authoritative for humans and LLMs       | CLI help, component READMEs                      |
| *Current evidence*   | Selected inputs, completed operations, unresolved work                           | =cga llm context …=, then referenced artifacts    |

I would align *task routing* with the same four human-facing groups, while retaining implementation-oriented topic notes underneath. A task such as “create databases” should lead to its commands, preparation contracts, representative example, and smallest relevant checks—not require reading every preparation document.

Two important boundaries:

- *Do not duplicate the human manual in agent notes.* Record constraints and link to authoritative explanations.
- *Do not put transient experiment state in permanent documentation.* Obtain it from read-only context commands and artifacts.

So: *human book = learning order; LLM guide = selective reading order; shared sources = facts.* We mostly need to sharpen the routing, not create another documentation collection.
